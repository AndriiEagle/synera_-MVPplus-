## 3. П’ять речей, які варто зберегти

1. **Згоду на конкретний зміст.** Version/hash, compare-and-set та дві незалежні approval не дозволяють непомітно замінити домовленість. Прийняття результату належить отримувачеві. Зменшення кількості полів не повинно перетворитися на автоматичне погодження. ([S-CLIENT], [S-CASE], [S-OUTCOME])
2. **Людський текст і контроль після помилки.** UI має окремі стани чернетки, зміни мови, закритої розмови, відмови та logout. Metadata-only retry не варто перетворювати на прихований outbox з автоматичним надсиланням. TA-02/03 треба виправити в цій архітектурі. ([S-JOURNEY], [S-STORE])
3. **Серверні межі приватності.** HttpOnly cookie, серверна перевірка identity, allowlist API, SQL permissions/RLS, public-only cache — доречні шари. Перевірки UI доповнюють їх. SQL lock ordering і tombstone для erasure мають історично перевірені конкурентні сценарії. ([S-WORKER], [S-ERASURE], [S-SW])
4. **Приватну картку без фальшивої репутаційної обіцянки.** Вона зручна як редагований авторський артефакт; це не незалежний сертифікат, доведена identity чи автоматично опублікований відгук. Зберегти повторну перевірку consent/session/text та escaping/CSP. ([S-CARD], [S-CLIENT])
5. **Правильний критерій продукту й чесні gates.** PRODUCT_DNA вимірює прийнятий результат, залишає Current default, Atelier добровільним, п’ять форм співпраці й AI необов’язковим. Явні OFF/pending корисніші за неправдиву універсальну «готовність». ([S-DNA], [S-PILOT])

Distribution / навчання / захист | Відтворюваний канал, корисний повтор, незалежність від Андрія | **Н/О** | Висока щодо межі | Repo assets і актуальні альтернативи | Є workflow/IP-кандидат; немає доведеного каналу; немає buyer evidence | Доступ до спільноти, повтор без concierge, законні права на дані | Друга незалежна когорта/оператор після першої; повтор і channel economics |

Навіть після усунення TA-01–04 ці оцінки не перетворяться автоматично на 90–100: буде виправлена реалізація, але попит, мобільна якість, операції й економіка потребують своїх доказів.

## 5. Три важелі й обмежений список робіт

Оцінки годин нижче — **планувальні припущення**, не комерційна пропозиція й не виміряна тривалість. `Eng` — інженерна робота з перевіркою; `Ops` — робота Андрія/оператора. Грошові витрати праці, пристроїв і провайдерів невідомі. Немає дозволу витрачати їх під час цього аудиту. Спільні verification gates можуть перекриватися: рядки не слід механічно складати як точний кошторис.

### Важіль 1. Людина підтверджує дію саме для того акаунта, який бачить

#### TA-01 — P1: неправильний actor при erasure після зміни cookie іншою вкладкою

**Факт → source → перевірка.** `app.mjs:606–625` бере локального actor, `NeonStore.eraseProfileData():40–52` надсилає лише `{confirm:'ERASE_APPLICATION_DATA'}`, worker:167–184 вибирає actor із поточної verified session. У request немає subject, якого щойно бачила людина. Репро original NeonStore зберігає локального A; модель спільної cookie перемикається на B; original worker спрямовує RPC із bearer B, а store приймає success. Можливість збереження A у confirmation UI встановлена читанням app; фактичний двовкладковий browser run не виконано. ([S-APP], [S-STORE], [S-WORKER]; `technical-repros.json`)

**Межа.** RPC був synthetic і нічого не стирав. Показано неправильне спрямування дозволеної self-only дії. Це не SQL authorization bypass; default-OFF gate робить finding blocker для активації, а не твердження про поточну шкоду live.

**Найменше рішення.** У наявних app/store/worker передати expected subject як умову confirmation; worker порівнює з verified subject **всередині цього POST до RPC**. За невідповідності — 409/clear confirmation, нуль mutation. Ціль SQL і надалі береться тільки з verified identity. Окремий GET перед POST не закриває гонку. Cross-tab notification допомагає UI, але не замінює server fence. Для зміни сесії того самого A потрібна opaque generation, якщо вона входить у контракт підтвердження.

**Зберегти:** self-only RPC, actor lock ordering, tombstone/admission, OFF flag, pending provider deletion, shared records, приватний purge лише відповідного контексту. **Залежності:** source-bound тест, worker session contract, browser cookie acceptance. **Ресурс:** Eng 6–12 год; Ops 1–2 год для двоакаунтного приймання; cash невідомий, додатковий paid AI не потрібний.

**Позитивний oracle:** A підтверджує свою дію, результат один, повтор безпечний. **Негативний:** A-display/B-cookie не запускає RPC, не стирає B і не повідомляє success; logout/revocation/late response не відновлюють приватне. Для нового входу того самого A спочатку зафіксувати контракт: expected subject сам по собі не розрізняє сесії; якщо confirmation прив’язане до generation, stale generation також має дати нуль RPC. **Stop:** будь-який wrong-subject dispatch. **Continue:** лише після actual two-tab browser proof і решти rollout gates; flag цим fix автоматично не вмикається. Очікувана користь — правильна адресація незворотної дії; величина avoided harm не оцінюється.

#### TA-03 — P2: запізнілий 401 прибирає нову cookie

**Факт.** Worker:263–264 очищує session cookie на 401 поза erasure; `/session` із null робить те саме:164–165. Якщо A401 повертається після успішного входу B, `Set-Cookie: ... Max-Age=0` може прибрати вже нову B cookie. `NeonStore.restore()` захищає JS state, але не керує обробкою HTTP cookie браузером. Original worker у delayed transport proof повернув саме цей header; fresh browser application ще не виконане. ([S-WORKER], [S-STORE]; `technical-repros.json`)

**Рішення:** прибрати безумовне cookie deletion зі stale read errors або прив’язати invalidation до перевіреної server generation; зберегти явний logout і заборону простроченому actor. **Ресурс:** Eng 4–8 год; Ops 0.5–1 год; cash невідомий. **Залежність:** узгоджений session contract TA-01; не потребує нової auth-платформи.

**Acceptance:** A401/null після входу B або нового A не руйнує нову сесію; обидва порядки завершення запитів; explicit logout і compromised/expired admission все ще відмовляють. **Stop:** виправлення робить invalid token придатним до data API або зберігає чужий UI. **Continue:** повернення користувача не вимагає випадкового повторного входу. Зменшення churn/support — гіпотеза до людського вимірювання.

### Важіль 2. Дозволена домовленість проходить увесь шлях без вигаданих внесків

#### TA-04 — P2: pure paid buyer дозволений, але editor і картка очікують бартерну форму

**Факт.** `profile-brief.mjs:35–51` і matching:173–184 допускають buyer без `offer_tags`, коли supplier покриває його потребу. Canonical `caseParticipantProblems():232–245` вимагає внесок кожного лише для `joint_project`. Однак `materialFromEditor():545–554` завжди створює дві capability deliveries, а helper:65–77 теж потребує skills обох. Це суперечить DNA:19 про взаємовигоду, яка не обов’язково є бартером 1:1. ([S-BRIEF], [S-MATCH], [S-CASE], [S-CLIENT], [S-SCOPER])

**Додаткове відтворення.** Через supported store API створено валідну one-way paid B→A домовленість, обидві approval, supplier submit, buyer check+accept, `outcome_confirmed:true`. Supplier `socialDraft()` відхиляється з «Некоректний час.»: client:366–370 шукає accept event від усіх participants; у supplier, який не отримував deliverable, його немає. Це synthetic source execution, не user-browser/SQL/live run. ([S-CLIENT], [S-VALUE]; `paid-oneway-card-repro.json`)

**Найменше рішення:** mode-aware editor/scoper у поточних owners: supplier має реальний deliverable, buyer — явну компенсацію й умови; не вигадувати buyer skill. Adapter приватної картки спирається на фактичне receiver acceptance конкретного внеску. Підтвердження грошових умов/факту оплати залишається окремим; не підставляти його як фіктивний acceptance другого deliverable. Referral теж перевірити на власному meaningful shape, не на двох reciprocal skill fixtures.

**Зберегти:** усі п’ять режимів, дві людські згоди, чесний scope paid terms без payment protection, exchange/joint_project вимоги, приватність картки. **Залежність:** canonical mode contract, fixtures із різними формами внеску, no-auto-consent. **Ресурс:** Eng 10–20 год; Ops 1–2 год; cash невідомий. Це локальне узгодження контрактів, не новий marketplace.

**Позитивний oracle:** buyer без offer → supplier → явна сума/валюта/умови → дві approval → один deliverable → buyer check/accept → private supplier card. **Негативний:** відсутня компенсація не стає нулем, supplier не самоприймає роботу, silence не є payment, редакція скидає попередні згоди, referral не створює consent третьої особи. **Stop:** fix вимагає підробленого accept event. **Continue:** meaningful сценарії всіх п’яти modes, а не лише перемикання enum у однаковій fixture. Очікувана користь — доступність реальної платної форми; попит на неї ще невідомий.

#### TA-02 — P2: дозволені українські умови відхиляються як завеликий request

**Факт.** HTML:29–30 дозволяє чотири textareas по 2000 символів. Чотири поля по 500 українських символів проходять canonical validation, але actual `saveTerms()` серіалізує 7214 UTF-8 bytes. Worker:64–73 має global 4096-byte cap і повертає 413. `ServiceError` не має специфічного 413 copy й повідомляє «Сервіс тимчасово недоступний. Спробуй пізніше». Повтор того самого body не допоможе. ([S-REAL-HTML], [S-CASE], [S-CLIENT], [S-WORKER], [S-ERROR]; `technical-repros.json`)

DB окремо обмежує `material::text` до 16384 bytes. Тому просте глобальне збільшення HTTP cap не виправляє контракт повністю. [S-CASE-SQL]

**Рішення:** один bounded UTF-8 бюджет для editor/canonical/API/DB із JSON overhead; route-specific limit для material; зрозуміла 413 помилка біля форми, яка залишає текст. Для OTP/малих RPC не відкривати великий необмежений body. **Ресурс:** Eng 4–8 год; Ops 0.5–1 год; cash невідомий. **Залежність:** остаточна форма material TA-04, UK/DE/EN copy.

**Acceptance:** ASCII, український текст і emoji нижче/на/вище межі; валідна max-boundary домовленість зберігається; завелика не зникає й не стає нескінченним retry. Перевірити реальне PostgreSQL JSONB представлення. **Stop:** розбіжність client/API/DB або очищення draft. **Continue:** людина розуміє, що саме скоротити. Зменшення відмов від заповнення — гіпотеза, не виміряна конверсія.

#### UX-01 — P2: завершення цінності й наступна дія мають бути видимими

**Факт і гіпотеза окремо.** `syncSteps():50–54` відмічає people → terms → invitation → conversation, хоча outcome UI уже існує. Порожні люди:98 не пропонують дію. Editor до першого запрошення збирає відразу обидві сторони, строки, права й умови. Це source facts; ступінь розгубленості або конверсійна шкода без людей не виміряні. ([S-JOURNEY], [S-REAL-HTML])

**Рішення:** одна видима наступна дія з її owner («Ти: перевір результат», «Чекаємо відповіді…»), окремий стан результату; progressive disclosure у тій самій формі, без приховування важливих умов перед згодою. Empty state: пояснити обмеженість пілота, запропонувати уточнити актуальну потребу/доступність; показувати тільки дії, які справді реалізовані. Не створювати фальшиву обіцянку «ми скоро знайдемо». На candidate card — конкретний відомий збіг і невідоме, без reliability score людини.

**Зберегти:** Current default, добровільний Atelier, ручний текст, keyboard/focus, відмову, мінімальні згоди. **Ресурс:** Eng 6–12 год; Ops 2–4 год для walkthrough; cash невідомий. **Acceptance:** новачок називає поточний стан/наступну дію/хто відповідає; 320–1440, 200% text і довга німецька copy не перекривають controls; collapse не ховає важливу зміну умов. **Stop:** краса збільшує кількість mandatory кроків або прибирає consent. Очікуваний виграш у зрозумілості потрібно перевірити.

### Важіль 3. Перевірити регулярну користь за повною ціною

#### G-01 — P1, evidence/operations gate: прийняти конкретний live-кандидат

Це **не newly proven bug**. Потрібні вже названі в handoff/pilot gates: signed JWT двох живих акаунтів із actual deployed SQL/grants; позитивний цикл і негативні self/peer/third-party/RLS/expired-consent випадки; restore/recovery на конкретному release; фізичні Android/iPhone; визначений owner support/data requests. Поточні local/synthetic receipts цього не замінюють. ([S-HANDOFF], [S-PILOT])

**Owner:** Андрій як release/operator decision maker + Codex для перевірюваного кандидата. **Найменше рішення:** закрити чинний чеклист точним source/release receipt, без нового governance framework. Privacy copy, retention по типах даних, backup/provider deletion і правові питання — розділ 10. **Ресурс:** Eng 6–12 год підготовки/усунення вузьких gaps; Ops 4–8 год плюс фахова privacy-перевірка, тривалість/ціна невідомі. Credentials, пристрої й дозволений rollout — зовнішні залежності; їхня наявність не припускається.

**Acceptance:** точні actor/source/environment/time й успішний recovery; на негативних доступах нуль unauthorized rows/actions. **Stop:** нез’ясований доступ, незворотна втрата або неперевірений restore. Erasure може лишатися OFF; full account deletion не заявляється. Live-пілот не починається на підставі документа без конкретного приймання.

#### B-01 — P1, business unknown: одна когорта, повтор і фактичний облік

**Owner:** Андрій. **Факт:** source називає попит, CHF12 і першу аудиторію гіпотезами; незалежні cohort/payment inputs не знайдено. **Рішення:** після G-01 до 10 пар з однієї доступної ніші, людська задача на 7 днів, origin relationship, відмови, outcomes, repeat, WTP і хвилини оператора. План у розділах 9–11. ([S-DNA], [S-PILOT])

**Ресурс:** Eng 0–4 год лише для мінімального журналу без raw private text; Ops 12–25 год плюс невідомий рекрутинг/збої. Ліміт часу й cash Андрій задає до старту. Paid AI для детермінованого/manual шляху не потрібний; hosting, payment/legal/device витрати від цього не стають нульовими.

**Acceptance:** добровільно прийняті реальні artifacts, зафіксовані також невдачі, виявлено хоча б початковий добровільний repeat і конкретну причину обрати Synera. **Негативний oracle:** founder coaching, synthetic people, прихований тиск чи фіктивна оплата не зараховуються. **Stop/continue:** заздалегідь задані управлінські пороги, жодної обіцянки PMF за 10 пар. Мета — вирішити, чи варта наступна інвестиція, а не виробити красиву funnel-картинку.

### Межа перебудови

Для оцінки масштабу беремо 12 одиниць: вхід; профіль; кандидат; умови; дві згоди; запрошення; розмова; дія; доказ; receiver acceptance; архів/картка; повтор. Пропозиція змінює насамперед **2 із 12 одиниць** — форму умов і adapter архіву/картки; це приблизно 17% за цією грубою продуктовою класифікацією, не частка файлів чи вартості. Session/input fixes перетинають кілька units, тому технічна вартість не пропорційна цим 17%. Повна перебудова на 20–30% не потрібна як квота. Новий backend, router, public reputation system чи AI-voice шар не обґрунтовані цими дефектами.

## 6. Повний шлях двох людей і три сценарії аудиту

### Сценарій A. Новачок із нечіткою потребою, людей мало

Найбільша перевірювана гіпотеза: людина платить увагою та даними до першої відчутної користі. Source дозволяє допомогу з формулюванням, але порожній список кандидатів не дає конкретного продовження. Мінімальна користь до matching — сформульований власними словами малий результат і зрозумілий критерій, який можна використати у звичному каналі. Перевірити: чи людина сама називає, що стало яснішим; чи зберігається шлях без AI. Спростування: helper додає більше переписування, ніж ручний опис, або поза красивим текстом немає актуальної задачі. ([S-SCOPER], [S-JOURNEY])

### Сценарій B. Зайнятий компетентний учасник, нерівні внески, скепсис до бартеру й AI

Це найсильніший негативний приклад до універсальної двосторонньої capability-форми: buyer може приносити гроші, доступ чи реферал, а не другу симетричну послугу. Платний one-way шлях у source допускається, але поточний editor/card його не проводять. Пріоритет — TA-04, короткі явні умови, право відмовитися від helper. Вартість полів вимірювати часом обох, а не тільки автора. Спростування продуктової гіпотези: обидва швидше й зручніше завершують ту саму справу за власною рекомендацією й не мають причини повертатися до Synera. ([S-DNA], [S-MATCH], [S-CLIENT])

### Сценарій C. Умови змінилися, затримка, відмова або спір

Наявні revision/approval/receiver rules — корисна основа збереження контролю. Не перетворювати «нейтральність L» на примус до компромісу: людина може мати достатню причину відмовитися. В UI важливо показати змінену редакцію, того, від кого чекають відповіді, факт часткового виконання й реальний наступний крок. Erasure не має обіцяти знищення спільної історії, а export не повинен виправдовувати її публікацію. Перевірити retry, expired consent, одностороннє відкликання, logout, мову, offline/resume на конкретному release. Новий browser proof тут відсутній; acceptance описаний для Codex. ([S-CASE], [S-CLIENT], [S-ERASURE])

## 7. «Можемо рухатися не туди»

### Найсильніша версія тези за Synera

Корисні професійні знайомства часто залишають невизначеними внесок, обсяг, строк і критерій завершення. **Гіпотеза:** для конкретної групи людей дешевше мати одну збережену малу домовленість із незалежними згодами й прийняттям, ніж щоразу координуватися вручну. Поточне ядро відповідає саме цій частині роботи; його можна перевірити без великої карти, realtime L-голосу й нової соціальної мережі. Це висновок із дизайну продукту та альтернатив, а не виміряна ринкова перевага. ([S-DNA], [C1]–[C5c])

### Найсильніша теза проти

Людям може бути потрібна сумісна й надійна людина, а не ще один workflow. Хороший контакт вони вже мають через рекомендації/спільноти; платну роботу — через платформи з оплатою й захистом. Тоді Synera додає форми, а її «успіхи» створює Андрій власними поясненнями та нагадуваннями. Accepted-кнопка й приватна картка можуть бути ввічливим завершенням, яке не породжує повторної користі. Це сильна перевірювана альтернатива, а не встановлений провал.

### Спостереження, яке розрізнить ці тези

Учасники приходять зі своєю задачею, мають звичну альтернативу, можуть відмовитися й завершують реальну роботу. Після цього вони **самі називають конкретну додаткову користь Synera, починають наступний цикл і за дозволеного billing обирають оплату**, при цьому час допомоги засновника не зростає до непосильної суми. Якщо цього немає, сильний код лишається активом, але інвестиція в ширший продукт не виправдана.

| Рішення | Що виграємо | Компроміс і умова |
|---|---|---|
| Продовжити широке поточне бачення | Швидко додаються нові поверхні й можливості | Ризик витратити час на неперевірений попит, складніший cold start/support. Зараз не рекомендую |
| **Звузити до однієї корисної співпраці й перевіряти попит** | Використовуємо ядро, локалізуємо баги, дешево відрізняємо координаційну цінність від discovery | Не доводить весь ринок; вимагає чесного журналу й права зупинитися. **Рекомендую** |
| Зупинити нову розробку до перевірки задач/альтернатив вручну | Мінімальні наступні engineering витрати | Не перевіряє сам workflow. Доречно, якщо зараз немає ресурсів для G-01 або доступної когорти; не потребує викидати код |
| Pivot-or-stop ширшого продукту | Припиняє витрати на непідтверджену модель | Рішення після слабкого повтору/економіки й сильнішої альтернативи, а не лише через відсутність поточних даних |

## 9. Економіка, ресурси й горизонт 12–24 місяці

### Повна вартість прийнятої співпраці

Позначення за один місяць: `Npaid` — фактично платні активні підписки; `P` — ціна; `Cusage` — hosting/AI/transport та інші змінні витрати **всіх спроб**; `Fpay` — payment fees; `Tsvc` — service/support/moderation/dispute години; `Tacq` — acquisition години; `w` — явно обрана ціна години. `Naccepted_cycles` — унікальні цикли з усіма належними receiver accept у тому самому вікні: один цикл рахується один раз незалежно від кількості внесків. `Ncompleted_agreements` із виконаною компенсацією — окремий знаменник. Кожний невідомий input лишається unknown.

```text
Gross subscription revenue = Npaid × P
Net subscription revenue = gross − refunds − applicable indirect taxes included in price
Contribution before fixed costs = net subscription revenue − Cusage − Fpay − Tsvc × w
Economic acquisition cost = acquisition cash + Tacq × w
Service cost per accepted cycle = (Cusage + allocated Fpay + Tsvc × w) / Naccepted_cycles
Full allocated cost per accepted cycle =
  (Cusage + Fpay + Tsvc × w + acquisition cash + Tacq × w
   + allocated fixed costs + allocated development cost) / Naccepted_cycles
Operating economic result before remaining applicable taxes =
  contribution − acquisition cost − fixed costs − allocated development cost
```

`Tacq` не треба ще раз включати в `Tsvc`: години не рахуються двічі. Cash result і opportunity cost часу слід показувати окремо. Розподіл fixed/development/acquisition між когортами й періодами треба явно записати; це управлінська економічна модель, не готова бухгалтерська звітність. Застосовні податки не віднімаються двічі; refunds і невідомі fees не вважаються нульовими. Якщо `Naccepted_cycles=0`, одинична вартість не нуль; показати витрати й відсутність результатів. Retention є cohort metric, а не трафік чи тривалість чату. ([S-DNA]; визначення — рекомендація цього аудиту)

### Ілюстрація чутливості CHF12 — не дані Synera

**Умовні inputs:** 60 активних людей; 20 платних × CHF12 = CHF240 gross; CHF60 Cusage; 10 accepted cycles; `w=CHF30/год`; тут acquisition, refunds, fees, taxes, fixed/development не включено, вони невідомі. Під «хвилинами» нижче — вся service/coordination/support праця для цих активних людей. Остання колонка — service cost, не повна собівартість бізнесу.

| Service хвилин на активну людину / місяць | Годин загалом | Залишок після usage і service labour | Вартість usage+service на прийнятий результат |
|---|---:|---:|---:|
| 1 | 1 | CHF150 | CHF9 |
| 6 | 6 | CHF0 | CHF24 |
| 12 | 12 | −CHF180 | CHF42 |

У цьому прикладі **6 хвилин обслуговування на активну людину вже з’їдають залишок** до payment fees, податків, fixed/development і залучення. Висновок залежить від припущень; це не виміряна збитковість Synera й не підстава автоматично підняти ціну. Дешевий AI не компенсує невидиму працю засновника.

Для клієнта CHF12 дорівнює вартості 24/12/7.2 хвилини за умовних CHF30/60/100 за годину. Зекономлений час не стає автоматично грошовим доходом. Потрібно дізнатися, чи користь регулярна, хто платить і чому конкретно CHF12 варто заплатити після безплатного пілота.

### Ресурси: що реально є й чого немає в доказах

Є повторно придатні modules, HTML/CSS/assets, canonical workflow, consent/retry/outcome guards, SQL generators, tests і historical evidence. Можна повторно використати deterministic scoper, private card, Current/Atelier й уже написаний pilot checklist. Кількість файлів або AI-підзадач не є командою підтримки.

Зовнішні залежності: доступні люди зі справжніми задачами; години Андрія; дозволені credentials/rollout; фізичні телефони; privacy/billing рішення; канал залучення. Їхня наявність і cash budget не встановлені. На пілоті доречна прозора ручна допомога, якщо її час рахують. Автоматизувати вже повторювану перевірку integrity/permissions; не автоматизувати невідомий попит новим agent swarm.

### «Мільйон» і можливий продаж

Не визначено валюту й метрику цілі. Потрібно розрізняти виручку, gross/operating profit, valuation, ціну угоди й гроші засновника. **Як арифметичний орієнтир:** `CHF12 × 12 × 6945 = CHF1,000,080` annualized gross subscription revenue. Це приблизно 6945 одночасних платних підписок, не прибуток і не вартість бізнесу. Даних для шляху до цієї кількості наразі немає.

| Умовний стан за 12–24 місяці | Що мало б бути доведено | Рішення |
|---|---|---|
| Downside | Потреба не повторюється або ручне обслуговування/спори поглинають цінність | Зупинити scale; зберегти й перевикористати workflow/IP, перевірити інший вузький job |
| Base | Одна ніша має добровільний repeat, фактичну оплату й прийнятну contribution | Підтримати нішу, обережно зменшувати повторну ручну працю, не заявляти великий ринок |
| Upside | Механізм працює у другій незалежній спільноті/з іншим оператором, є відтворюваний acquisition і чисті права на дані | Розглядати розширення й strategic partnerships на фактах |

Цим сценаріям не присвоєно прогнозів виручки, ймовірностей або valuation: input недостатньо. Потенційно цінні активи — повторювана корисність, добровільна щільна мережа, законно отримані дані, довіра до accepted workflow, бренд/IP й мала залежність від Андрія. Оператор професійної спільноти або workflow-платформа — можливі **типи** стратегічного покупця, не встановлені зацікавлені сторони. Prompts/animations самі по собі захисту не доводять.

## 11. Мінімальний чесний експеримент із людьми

**Це план. У цьому аудиті нікого не рекрутували, не запрошували, не реєстрували й не просили платити.** Live застосунок потребує G-01. До нього Андрій може за окремим власним рішенням перевіряти формулювання задач у звичному способі, але така розмова не є runtime acceptance Synera.

### Кого й навіщо

Перша гіпотеза сегмента: незалежні web/design/AI-services фахівці з однієї доступної Zürich-спільноти, у яких **вже є конкретний artifact і задача на наступні 7 днів**, а не лише загальне бажання нетворкінгу. Приклад можливого job: один landing page / flow / невелика автоматизація, для якої потрібен обмежений зовнішній внесок і ясний критерій. Це рекомендація для рекрутингу, не опис уже наявних клієнтів.

Спочатку двоє людей окремо проходять runtime acceptance і негативні відмови. Їхня допомога засновнику не зараховується автоматично як market demand. Далі діагностична когорта **до 20 добровольців / до 10 різних пар**, або заздалегідь заданий ліміт операторських годин, що настане раніше. Чисельність дозволяє побачити кілька типів зриву за малих витрат; вона не статистично доводить PMF чи перевагу на ринку.

**Super Idea — «Приведи свого партнера» як окрема діагностика.** Дві-три вже знайомі пари перевіряють, чи корисний сам workflow без проблеми пошуку. Окремо нові сумісні люди перевіряють discovery. Без спеціального експериментального дизайну це не randomized control group. Успіх знайомих пар не доводить matching, органічний попит незнайомців чи мережевий ефект. Якщо навіть знайома пара не отримує додаткової користі порівняно зі своїм звичним каналом, масштабувати discovery рано.

Запрошення має чесно називати безплатний прототип/пілот, зміст збереження, строк участі й право вийти. Не вимагати клієнтських секретів, публікації картки або похвали засновника. Збір feedback — окремо від оцінки особи. Пару можна не створити; unmatched і відмови лишаються у журналі.

### Що саме означає успіх

**`deliverable_accepted`:** належний отримувач переглянув фактичний результат і окремо підтвердив погоджені критерії актуальної редакції. У exchange — окремо кожний обіцяний внесок. **`agreement_obligations_completed`:** усі зобов’язання конкретної угоди виконані; для paid прийняття роботи саме по собі не доводить грошей. У запропонованому журналі пілота виконання компенсаційного зобов’язання слід вести окремо: «не настала / очікується / підтверджена / оскаржується». Це запропонований облік; поточний `compensation.status` описує погоджені умови, а не доказ платежу. Не створювати фіктивний другий deliverable чи accept. **Оплата Synera CHF12 — третій окремий факт**, не гроші між учасниками. [S-CASE]

Для двох-трьох схожих задач добровільно зафіксувати, як люди вже діють у своєму звичному каналі: коротка нотатка часу, результату й причини вибору, без копіювання приватних переписок. Це мала convenience comparison, не causal A/B-proof. Порядок показу helper/manual записати, бо він може впливати на досвід.

### Журнал із подіями й знаменниками

| Метрика | Визначення й знаменник |
|---|---|
| Intake/discovery funnel | Invited → eligible → admitted → є конкретна потреба → запропоновано пару → дві згоди → дія → accepted. Абсолютні n/N на кожному переході; усі unmatched і відмови зберігаються |
| Походження | BYOC/discovery; prior relationship; джерело набору; унікальні people/dyads; first/repeat cycle. Знайомі й нові пари звітуються окремо |
| Прийняття результату | Accepted cycles із усіма належними receiver accept / усі розпочаті цикли, для яких закінчилося вікно спостереження. Окремо accepted / усі запропоновані пари |
| Виконання угоди | Agreements із виконаними всіма зобов’язаннями / всі угоди з завершеним належним строком; payment pending/dispute не приховується в accepted |
| Час до першої користі | Від першої згоди на участь до першої підтвердженої користі; time-to-pair і time-to-outcome окремо. Невдалі/незавершені показати поруч, не вилучати мовчки |
| Відмова, затримка, спір | Кількість і конкретний перехід / всі релевантні спроби. Відмова може бути правильною; не карати її rank чи примусом |
| Добровільний repeat | Люди, які самі розпочали другу реальну справу за 30 днів / люди з першим accepted outcome і **повним 30-денним вікном**. Окремо результат повтору; не складати shared-user cycles як незалежні |
| WTP | Конкретна відповідь на прозору CHF12/місяць пропозицію / всі, кому її фактично показали; причина «ні», платник, очікувана частота користі |
| Фактична оплата Synera | Завершені дозволені платежі / люди, які отримали реальну платну пропозицію; продовження окремо. До billing gate — **не виміряно**, не «0% попит» |
| Повна вартість | Cusage всіх спроб, Tsvc/Tacq, setup/repeat, cash/time окремо; cost per accepted і completed agreement, включно з невдачами |
| Захисні метрики | Непогоджені зобов’язання AI, тиск/скарги, витік, примусова публікація, withdrawal, невирішений спір. Мінімізувати персональні дані й зберігати контекст для розбору |

Коротший час у застосунку може бути добрим результатом, якщо люди виконують справу поза ним. Метрики мають бачити обидві сторони, а не лише того, хто натискає кнопку чи платить.

### Правила продовження й зупинки

Пропозиція до старту: review після максимум 10 пар або ліміту часу. **Умовний continue:** щонайменше 6/10 повних спостережуваних перших циклів дали прийнятий результат без тиску; щонайменше 3 людини самі назвали й почали другу справу; є конкретна додаткова користь Synera, немає невирішеної шкоди даним/згоді. Це **управлінські припущення**, які треба зафіксувати до перегляду результатів, не статистичні стандарти. Продовження конкретного сценарію вирішується також за його окремими результатами: успіх BYOC не компенсує непідтверджений discovery.

Якщо строк дозрів лише для 8, показати `n/8 + 2 pending`, а не добрати зручний знаменник. Пари з тими самими учасниками залежні; N=10 не дає підстав удавати точний confidence interval чи незалежність. Completion після ручного вибору найкращих пар не приховує intake, де люди лишилися без партнера.

**Narrow/fix:** зриви концентруються в одному переході, а люди все ж приходять із наступною реальною задачею. Виправити цей owner й перевірити наступною малою когортою. **Stop expansion:** користь потребує постійного concierge, ніхто добровільно не повертається або звичний безплатний спосіб стабільно кращий. **Негайно призупинити уражений шлях:** підтверджена приватна шкода чи порушення згоди незалежно від conversion. Гіпотезу ціни тестувати після користі, без прихованого списання і без обіцянки вже активного billing.

### Що відкласти

Повний redesign, новий стек/AI-router, realtime model voice/video, примусове gamification, public reputation scores, автоматичну публікацію карток, нові CHF49/249 tiers і pitching гарантованого продажу. Це не заборона назавжди: кожну можливість можна повернути після конкретного доказу, що вона усуває вузьке місце чинної пари.

Performance optimization також має починатися з вимірювання: `socialDraft()` повторно читає case/approvals/outcomes для коректності; можна дослідити вузький authorized snapshot/RPC, якщо p95 справді заважає. Прибирати fresh revalidation заради удаваної швидкості не слід. Latency/cost saving наразі unknown.

## 13. Вирішальні невідомі, два питання й один NEXT

Невідомі: paying users; частота природного repeat; доступ до конкретного каналу; доступні години/runway; фактичні Cusage/Tsvc/Tacq; deployed grants/auth; повний account-deletion/backup process; billing; новий render і фізичні пристрої; законні права на всі майбутні дані/внески; стратегічні покупці. План/fixture не замінює жоден із цих inputs.

Два питання, відповіді на які справді змінять рішення:

1. **Який ліміт годин і грошей ти готовий виділити на 30-денну перевірку до наступного рішення, включно з ручною допомогою й невдалими спробами?**
2. **Яку одну вже доступну тобі спільноту й яку повторювану конкретну задачу її учасників ти знаєш із власних розмов?**

Ці питання не блокують виконаний аудит і не є проханням повторно дозволити push.

**NEXT на 15 хвилин:** заповнити одну картку без імен/повідомлень людям: «A вже має ___; до ___ потребує ___; B реально дає ___ й отримує ___; receiver приймає, якщо ___; оплата/інші зобов’язання ___; звичний спосіб сьогодні ___». Якщо картку не можна зробити конкретною без фантазій, спочатку перевіряти задачу. Довші залежності: TA-01–04, G-01, ресурсний cap і окремо дозволений рекрутинг/billing.

## 14. Три кінцеві проходи якості

1. **Факти.** Звірено pinned owners і відтворення; raw receipt mismatches виявилися LF/CRLF-equivalent, тому не названі drift-багом. Два sandbox bind failures закриті тими самими original тестами й не подвоїли кількість cases. MIT v2 не приписано causal шкоду voice; у Stanford розведено published 2405 і preprint 1604; Conlon methods 1510 не підмінені abstract rounding. Current visual залишено Н/О.
2. **Спростування.** Атаковано три рекомендації: narrowing може лише приховати відсутність попиту; BYOC може підтвердити звичну допомогу друзям; CHF12 можуть непомітно субсидувати години Андрія. У відповідь додано звичну альтернативу, origin relationship/unmatched funnel, добровільний repeat, окремі accepted/compensation/subscription events і cap витрат. Не підвищено оцінки за красиві локальні tests.
3. **Практичність.** Залишено три важелі, одну P1 finding family, evidence/business gates і обмежені P2; current owners, minimum fixes та stop/oracle є для кожного. Замість загального redesign — mode/actor/input repairs. Відкинуто безумовний statistical interval для 10 пар: shared users і convenience cohort не дають незалежних спостережень. Live authorization не підмінена report completion.

Це три різні проходи одного аудиту з паралельними підзадачами, не три незалежні сертифікаційні моделі. Основний висновок після self-review зберігся: **ядро варто довести до перевірюваного вузького використання; подальшу широку інвестицію має виправдати поведінка людей.**
