# Synera: двосторонній шлях, системи й межі приймання — 03.10.2026

**Стан: LOCAL_ACCEPTED_RUNTIME_HOLD.** Це завершене локальне доповнення до наявного продукту, а не приймання всього живого сервісу. Поточні акаунт, профіль, matching, кейси й повідомлення з'єднані в окремому `/real-journey.html`. Чинні екрани та режими дизайну збережені.

## Що завершено в цьому доповненні

1. Людина входить через наявну оболонку `/index.html`, заповнює власний профіль і відкриває реальний двосторонній шлях.
2. Система показує наявні відкриті профілі й пояснює відповідність оголошених give/need. Тестові персонажі не підставляються у реальний екран.
3. Учасник заповнює спільні умови: що кожен дає, який результат отримує, як його прийняти, дати й правила. Порожні поля не стають згодою.
4. Кожен переглядає одну й ту саму поточну редакцію та сам підтверджує свою сторону. Немає автоматичного «так» за мовчанням.
5. Лише після двох чинних підтверджень можна надіслати запрошення. Адресат сам приймає або відхиляє його.
6. Приватна переписка відкривається після прийняття. Це фактично збережений текст учасників, а не імітація відповіді AI.

Порядок «обидва підтвердження → запрошення → прийняття → повідомлення» успадковано від чинного SQL. Чат до підтверджень та підтвердження фактичного виконання/оплати не входять до цього доповнення.

## Виправлені конфлікти й захист стану

- Зміна умов використовує точний попередній case ID, version і SHA-256. Якщо інша сторона встигла змінити їх, запис відхиляється з конфліктом, а її матеріал зберігається. Це перевірено для нового й попереднього ProfileStore.
- Конкурентна редакція з тим самим номером також не перезаписує вже збережену іншу редакцію.
- Власне підтвердження записує тільки власний approval; матеріал не PATCH-иться. Нова редакція робить попередні підтвердження нечинними.
- Шлюз не пропускає PATCH матеріалу без точних предикатів. Новий rollout gate закриває обидві case-таблиці до запитів до Auth/Data API.
- Формати дат PostgREST з часовим поясом і дробовими секундами нормалізуються на клієнті без зміни SQL-даних.
- Наявний paid-кейс показує суму, валюту, рахунок, результати та критерії до підтвердження. Новий редактор цього екрана створює взаємний обмін; він не створює платіж і не списує гроші.
- Зміна розмови прибирає стару чернетку; запізніла відповідь старої розмови ігнорується. Вихід, втрата сесії або доступу очищають приватний екран, включно з незавершеним читанням.

## Системи: що реально є, а що лишається

«Наявне» нижче означає присутній код/попереднє обмежене приймання. Поточна незалежна перевірка стосується саме двостороннього доповнення; історичні докази інших систем наведені у [START_HERE](../../START_HERE.uk.md).

| Система | Фактичний стан | Що відділяє її від живого запуску |
|---|---|---|
| Презентаційний сайт і fictional demo | Окремий раніше опублікований сайт; вигадані учасники та демонстраційні сценарії | Публікація не доводить live продукт, доступність з усіх пристроїв чи реальні угоди |
| PWA й мобільна оболонка | Наявні manifest, offline режими й інструкції Android/iPhone | Фізичний Android цього кандидата не прийнятий; native APK/App Store немає |
| Акаунт, OTP і власний профіль | Наявний Neon/Worker транспорт; новий UI його використовує | Два справжні Neon акаунти та поточний provider JWT ще треба перевірити |
| Give & take пошук | Наявний детермінований двосторонній matcher за заявленими даними | Семантична сумісність, психологічна «іскра» та прогноз успішності не доведені |
| Спільні умови та незалежна згода | Новий зв'язаний UI, версії, власні approvals, захист конкурентних записів | Поточне SQL/RLS приймання й live застосування відсутніх міграцій |
| Запрошення та приватний текст | З'єднані з умовами й прийняттям; браузерний цикл пройдено | Auth/Data API у поточному тесті — fixtures, не live Neon |
| Карта й місце зустрічі | Наявні окрема demo-карта, Maps URLs, адресний/маршрутний та consent-bound location код | Вбудованого Google SDK немає; KV binding, реальна локація та маршрут нового UI потребують live приймання |
| Блокування, скарги, контроль доступу | Наявні шари правил; новий екран перевіряє учасників і сесію | SQL/RLS/JWT атакувальне приймання на поточному runtime, зокрема outsider/revoke |
| Triangle L і групова кімната | Окремі локальні режими й підготовлений мережевий код/SQL | Мережева кімната не прийнята: group gate лишається вимкненим |
| AI і голос/відео | Попередній явний локальний AI-адаптер; демонстраційні сценарії | Публічний LLM, голосовий onboarding, тристоронні calls і керування мікрофонами не запущені |
| Архів і соціальний пакет | Studio має добровільний власний архів, точні цитати й підтверджені чернетки | Публікація LinkedIn/Instagram, OAuth й автоматичні пости не підключені |
| Радари, джерела подій і підбір команди | Вимоги збережені; новий двосторонній шлях не видає їх за готові | Офіційні джерела/дозволи, актуальність, ranking і виконання за згодою |
| Тарифи, купівля й оплати | Обрано тимчасово безкоштовний Zürich-пілот; paid-умови можна переглянути | Checkout, платежі, чинні тарифи й приймання billing не завершені |
| Телеметрія й адаптація дизайну | Збережені ручні opt-in режими та наявні локальні докази | Немає підстав заявляти постійну автономну оптимізацію, виміряні гормони чи приховане відстеження |
| Компресія/пам'ять AI | Власні нотатки та структурований контекст мають різні призначення | Немає приймання універсального «перекодування без втрати сенсу» або виміряної економії токенів для цього циклу |

## Як має почуватися користувач на кожному кроці

Це цілі дизайну й гіпотези для добровільного user-тесту. Браузерні тести перевіряють поведінку інтерфейсу, а не емоції, гормони чи психологічний стан людини.

| Крок | Відчуття, яке підтримуємо | Конкретне UX-рішення й перевірка з людиною |
|---|---|---|
| Сайт | «Розумію, для чого це мені» | Чітке розділення презентації, демо й реального пілота; запитати, чи людина може пояснити цінність своїми словами |
| Вхід | «Знаю, куди потрапляю і що дозволяю» | Наявний вхід і чинна політика; без підміни акаунта ботом |
| Профіль | «Можу показати потрібне й залишити приватне при собі» | Заявлені give/need й керована видимість; перевірити, чи зрозуміло, хто бачить дані |
| Підбір людини | «Бачу взаємну користь, а не магічний рейтинг» | Пояснення відповідності реальних заявлених полів; дати людині самій обрати |
| Чернетка умов | «Ми можемо домовитися конкретно» | Явні результати й критерії кожної сторони; редактор відкривається за потреби |
| Перегляд редакції | «Розумію, з чим погоджуюсь» | Повний матеріал, версія, дати, сума/валюта/рахунок наявного paid-кейсу |
| Власне підтвердження | «Мій голос не підмінять» | Власний checkbox і кнопка; мовчання не згода; застаріле підтвердження відхиляється |
| Очікування другої сторони | «Знаю, що ще потрібно, і можу відмовитися» | Окремий стан обох approvals і власне відкликання; без примусу або фальшивої активності |
| Запрошення | «Наступний крок простий і зрозумілий» | Надсилання тільки після обох approvals; адресат має явне прийняти/відхилити |
| Розмова | «Є спокійне місце для дії» | Окремий блок, зрозуміле поле й одна дія; інші секції згортаються |
| Зміна умов | «Зміни помітні, старої згоди недостатньо» | Нова редакція скидає чинність approvals; конкурентний запис не губиться |
| Вихід | «Мої приватні дані більше не на екрані» | Негайне очищення й відкидання запізнілих відповідей; приватного browser storage у новому екрані немає |
| Після реальної зустрічі | «Бачу результат і можу ним поділитися добровільно» | Наявні Studio-чернетки й власний архів окремі; доказ виконання і social publication — наступний незавершений цикл |

Мета — добровільно повертатися через корисний результат. «Залежність», гарантований нейрохімічний ефект чи прихована психологічна координація не є критерієм приймання.

## Де дані

Реальний клієнт повторно використовує наявний NeonStore/HttpOnly-сесію: профілі, match_cases, match_case_approvals, meeting_requests і повідомлення живуть у серверних таблицях. Перевірка таблиць у цьому циклі виконана через ізольовані локальні fixtures; фактичне live збереження має окреме приймання. Новий екран не створює паралельну базу, ledger чи router і не зберігає приватний стан у localStorage, sessionStorage, CacheStorage або IndexedDB.

Окремий Studio-архів має власну явну згоду на IndexedDB. Серверний backup/recovery, retention, експорт/видалення й архівування production-бази потрібно звірити у фактичному проєкті; їх не можна оголосити налаштованими з наявності кнопки або локального ZIP. Сирі нотатки й скорочений AI-контекст не взаємозамінні: стислий виклад може втратити нюанс, тому точні цитати зберігають посилання на оригінал.

## Що треба для активації

1. Ізольований PostgreSQL runtime без Docker або інший погоджений disposable runtime. У поточній сесії встановленого runtime не знайдено. Не встановлювати його без точного дозволу.
2. Запустити канонічні base/case/group acceptance й негативні RLS перевірки на тимчасовій БД. Зберегти старі case/location докази; вони не замінюють новий group SQL. Окремо перевірити строк дії відкритого кейсу й можливість коректно закрити/поновити його: expiry/update gate та один open-case на пару можуть блокувати повторний цикл.
3. Звірити фактичні live міграції та recovery point. Frozen base уже застосовувалася — не повторювати її в production. Нова production-міграція потребує окремого точного дозволу.
4. Перевірити дві незалежні реальні сесії Neon/Auth/Data API: спільний case, зміна версії, обидва approvals, outsider, revoke, invitation, accept і повідомлення.
5. Лише після приймання опублікувати погоджений кандидат і ввімкнути потрібний gate. `SYNERA_REAL_JOURNEY_READY` та `SYNERA_GROUP_ROOMS_READY` залишити вимкненими до їхніх власних перевірок. Пройти встановлення й повторний цикл на фізичному Android.

Нове SQL не застосовувалося, Docker/production/публічний сайт не змінювалися. Головний ризик: позитивний fixture-тест не доводить поведінку справжніх SQL/RLS/provider cookies; тому runtime HOLD збережено.

Models used: none (provider calls=0, USD=$0.00). Використання основної підписки та її економія не вимірювалися.
