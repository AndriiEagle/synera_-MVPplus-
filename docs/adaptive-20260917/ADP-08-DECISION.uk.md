# ADP-08 — одна цільова функція: рішення й доказ

**Статус: DECIDED_FOR_SOURCE_REVIEW.** Це рішення про форму цільової функції плюс референсна реалізація з прогнаною перевіркою. Не production matcher, не диспатч, не витрата. `dispatch_allowed` лишається `false`.

Усе, що нижче стверджується числами, пораховано `adp08_matching.py` у цій сесії на синтетичних даних. Файл поруч, запускається одною командою, 9/9 перевірок проходять. Provider calls: 0. $0.00.

## 1. Рішення

У репозиторії лежали дві формалізації, і їх ніхто не порівняв:

```
MATH.uk.md          w_ab = min(u_ab, u_ba),   max Σ w_ab·x_ab,  Σ_incident(v) x_ab ≤ cap_v
ki-math-extract.md  F(z) = bᵀz + ½zᵀMz − λ‖z‖₀,  M = S − C
```

**Обрано: `min(u_ab, u_ba)` як вагу ребра. Адитивна форма відхилена для вибору пари.** Штраф λ і обмеження місткості з другої форми зберігаються, але переносяться з вершин на ребра — див. §3.

Підстава — не смак. E1 у прогоні:

| | вибір | сума |
|---|---|---|
| `w_min` | `a–c` | 4 |
| `w_sum` | `a–b` | 10 |

де пара `a–b` оголошена як `u_ab = 10, u_ba = 0`, а `a–c` — як `4, 4`. **Адитивна форма обирає пару, у якій друга людина не отримує нічого**, і робить це саме тому, що сума приховує односторонній нуль. Для продукту, чия єдина обіцянка — взаємна вигода, це дискваліфікує форму, а не параметр у ній.

Це також єдина форма, сумісна з трьома вже прийнятими рішеннями: C36 («не загальний рейтинг людини»), D14 («missing evidence не карати»), acceptance P09 («not negative competence or automatic credit penalty»). `min` дає стан **ребра**, а не бал людини: одностороння пара просто падає у вазі, і жодне число не чіпляється до профілю.

## 2. Структурна знахідка: `b_i` у продукті дорівнює нулю, і це ламає перенесення режимів

`ki-math-extract.md` побудований навколо трьох режимів за відношенням `λ/b`, де `b_i` — користь виконавця, що працює **сам**. У флоті це осмислено: один воркер сам робить задачу.

У Synera учасник сам не виробляє співпраці. Одиниця продукту — пара. Отже `b_i ≡ 0`, і тоді:

- `F(z) = ½zᵀMz − λ‖z‖₀`;
- критерій «пара б'є обох одинаків» `M_ij > λ − min(b_i,b_j)` вироджується в `M_ij > λ`;
- **таблиця трьох режимів за `λ/b` не переноситься взагалі** — при `b = 0` відношення не визначене, а формальний висновок «завжди режим дорогої координації, k=1» був би просто неправильним прочитанням.

Сам критерій коректний — E3 перевірив його на 20 000 випадкових інстансів, 0 розбіжностей із брутфорсом. Некоректним було б перенести разом із ним режимну таблицю. Фіксую це явно, бо саме такі перенесення й губили контекст у попередніх передачах.

## 3. Куди подівся λ: з вершин на ребра

`‖z‖₀` у формі флоту штрафує **активацію учасника**. У Synera координація коштує не на людину, а на **кожну активну співпрацю**: домовитись, звіритись, довести до проби. Тому:

- `λ` переїжджає у вагу ребра: `w_e = min(u_ab, u_ba)·f_e − λ_e`;
- обмеження «скільки паралельних співпраць витримує людина» — це **місткість вершини** `cap_v`, а не штраф.

Це рішення моделювання, не теорема: я його позначаю саме так. Але воно не нове для проєкту — `cap_v` уже існує як задача **V6-10 (per-person proposal limits, M07)**. Тобто ADP-08 не додає обмеження, а вказує, куди наявне обмеження вбудовується.

## 4. Підсумкова форма

```
Для кожної невпорядкованої пари e = {a,b}:

  1. Hard constraints першими:
       state(e) = INELIGIBLE          якщо режим не дозволений обома або немає доступності
                = NEEDS_INFORMATION   якщо u_ab або u_ba невідома
                = ELIGIBLE_SCORED     інакше

  2. Тільки ELIGIBLE_SCORED входить в оптимізацію:
       f_e = 2^(−age_e / half_life)              свіжість, 0 < f ≤ 1
       w_e = min(u_ab, u_ba) · f_e − λ_e         вага ребра

  3. max Σ_e w_e·x_e
     s.t. Σ_{e ∋ v} x_e ≤ cap_v,  x_e ∈ {0,1}

  NEEDS_INFORMATION не отримує ваги 0 — він іде в окремий видимий шлях
  (needs_information або дозволений ручний шлях, як каже MATH.uk.md).
```

E9 проганяє це наскрізь на інстансі з усіма трьома станами одночасно: одностороння пара не обрана, невідома винесена в `needs_information`, недоступна пара недопустима незалежно від ваги, свіжість `2^(−60/30)=0.25` застосована до ваги, не до допустимості.

## 5. Що перевірено прогоном

| Перевірка | Результат |
|---|---|
| E1 дві форми розходяться | `w_min` → `a–c` (4); `w_sum` → `a–b` (10, з них 0 для b) |
| E2 контрприклад greedy з `MATH.uk.md` | greedy 9 (`A–B`); оптимум 16 (`A–C`+`B–D`) — підтверджено |
| E3 критерій «пара б'є одинаків» | 20 000 інстансів, 0 розбіжностей із брутфорсом |
| E4 UNKNOWN ≠ 0 | вибір змінюється у **16.8%** з 4000 інстансів; у сконструйованому випадку примусовий нуль стирає сигнал `needs_information` без сліду у виводі |
| E5 свіжість — множник, не ворота | `w(0)=1`, `w(half_life)=0.5`, 5000 перевірок, 0 порушень; ніколи не перетворює недопустиме на допустиме |
| E6 монотонність місткості | 3000 інстансів, 0 порушень: зниження `cap_v` не підвищує оптимум |
| E7 детермінізм ≠ справедливість | n=5, усі ваги рівні: `e` має **0 появ із 200 раундів**, решта по 200 |
| E8 межа точного оракула | щільний граф: n=12 → 452 мс, n=14 → **20.6 с**; 20 учасників: 10% щільності → 1.1 мс, 20% → 14.3 мс, 30% → 335 мс |
| E9 підсумкова форма наскрізь | усі три стани поводяться як описано |

**E7 варто прочитати окремо.** Постійне сортування за ID при рівних вагах не «нейтральне»: при непарній когорті одна й та сама людина не потрапляє в підбір **жодного разу** — 0 із 200. При парній когорті спред 0, тобто проблема невидима. Це рівно те, про що попереджає `MATH.uk.md` («fairness перевіряється окремо, не називається доведеною детермінізмом»), тепер із числом.

**E8 задає інженерну межу.** Точний перебір годиться до ~12 учасників на щільному графі. Пілот P14 — це «10 disjoint pairs», тобто **20 учасників**, і там усе вирішує розрідженість графа допустимості: при 30% щільності 335 мс, при 100% — недосяжно. Висновок: точний оракул лишається як еталон і для малих когорт, але масштабування вимагає перевіреного b-matching solver, як `MATH.uk.md` і каже.

## 6. Виправлені твердження — три мої власні помилки

У стилі `ki-math-extract.md` §10 лишаю їх, а не прибираю.

1. **E4, перша редакція.** Стверджувала, що примус UNKNOWN→0 залишає людину зовсім без підбору. Прогін це спростував: при шести учасниках у людини зазвичай є інші оцінені ребра, тому вона все одно матчиться. Правильне твердження вужче й перевіряється: примусовий нуль **знищує сигнал `needs_information`** — пара зникає з результату без названої причини. Вибір при цьому змінюється у 16.8% випадків.
2. **E7, перша редакція.** Виміряла спред на **парній** когорті, отримала 0 — тобто дані суперечили заяві, — і все одно позначила перевірку як PASS через хардкод. Це саме той фальшивий зелений, який цей пакет узагалі не має права містити. Виправлено на непарну когорту, де ефект реальний і вимірюється.
3. **E8, перша редакція.** Стверджувала, що перебір покриває пілот P14, і «доводила» це виміром при n=10. Помилка подвійна: «10 disjoint pairs» — це 20 учасників, а не 10; і головний чинник не n, а щільність. Виправлено, тепер вимірюються обидві осі.

## 7. Що лишається UNKNOWN

`u_ab` — це **заявлена людиною** оцінка корисності конкретної співпраці. Її формат, шкала й спосіб збору не визначені й не вимірювані цим документом. `λ_e` (вартість координації однієї співпраці) і `half_life` свіжості не виміряні. Поки їх немає, форма коректна, а входів до неї немає — рівно так, як `ki-math-extract.md` закінчує сам себе.

Не роблю тут і не обіцяю: stable matching за preference lists — це інша мета, ніж max-weight allocation, і обидві одночасно не обіцяються (`MATH.uk.md`). Multi-party цикли — окремий майбутній контракт, не цей парний оптимізатор.
