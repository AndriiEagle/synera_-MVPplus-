# Synera: карта можливостей, Triangle L і безкоштовний Zürich-пілот

Дата зрізу: 02.10.2026. Це доповнення до `PRODUCT_VALUE_AND_SALES.uk.md`, а не заміна чинного продукту. Вхід: `/triangle.html`; попередня презентація й чотири основні екрани збережені. Поточна авторська версія є локальним прототипом на одному пристрої.

## Продуктова теза

Synera допомагає солопідприємцю пройти шлях **потреба → доречна людина → зрозуміла домовленість → зустріч → перевірений результат**. Карта показує можливості поруч. L дає трьом людям простір сформулювати внески та зробити наступний крок. Цінність потрібно перевіряти реальними завершеними колабораціями; кількість профілів, тривалість сесії чи ефектна анімація не доводять її.

Цільова аудиторія як робоча гіпотеза: солопідприємці, незалежні фахівці та малі команди в Zürich, які мають компетенцію, конкретну потребу й мало часу на пошук партнера. Не припускаємо психотип або стать за цифровим слідом. Потребу в підтримці запитуємо в людини, а не виводимо з кліків.

## Що вже матеріалізовано в цій версії

- Окремий вибір «Трикутник L / Жива карта / Запуск», без перебудови чинного workspace.
- Локальна кімната: три різні позначення людей, п’ять форматів, ціль, внески, текстові нотатки, відповідальні й виконання кроків, добровільна черга, явний JSON-експорт.
- Бюджет у цілих рапенах: CHF 1000 при рівних частках → 333.34 / 333.33 / 333.33. Це математично точний розподіл суми, а не доказ справедливості праці чи власності.
- Відповіді «так / ні / утримуюсь», відкликання, дедлайн. Лише три явні «так» поточної версії дають статус локально записаної одностайності. Нова пропозиція або зміна внеску очищує відповіді. Мовчання після дедлайну не створює згоди.
- L відповідає простими правилами на клік: невказані внески → один перевірний крок → завершення відкритого кроку → перевірка результату. Модель AI не підключена.
- Схематична карта з чітко вигаданими людьми, подією й проєктом; шари, вибір аватара, пояснення взаємодоповнення. Анімація враховує системний reduced motion.
- Порівняння місць за введеними оцінками часу й межами кожного; не використовує GPS, погоду або Routes API.
- Публічне рішення «тимчасово безкоштовно, CHF 0» та симулятор витрат лише Maps/Route Matrix. Без фальшивого лічильника користувачів, checkout чи автоматичної оплати.

Нотатки існують лише в пам’яті вкладки. Імена й відповіді може вводити одна людина; це не незалежно підтверджені учасники, не угода, не перевірка особи. Експорт містить імена/внески/бюджет; текст розмови додається лише окремою пташечкою. Закриття вкладки втрачає неекспортовані дані. Немає прихованої телеметрії, запису медіа або серверної передачі цих нотаток.

## Карта: рішення й офіційна економіка

«Вбудована карта» та «API-виклики» не є альтернативами: керована Google-карта в браузері використовує Maps JavaScript API. Для наших аватарів, вибору людей і накладених шарів обираємо **Maps JavaScript API**, після конфігурації ключа, обмежень і бюджету. Google документує [HTML/CSS-маркери](https://developers.google.com/maps/documentation/javascript/advanced-markers/html-markers); це потрібна технічна можливість, а не готова Synera-інтеграція.

| Варіант | Корисність для Synera | Рішення |
|---|---|---|
| Google Maps URLs | Відкрити адресу/маршрут у Google Maps; ключ не потрібен | Залишається для дороги на зустріч |
| Google Embed iframe | Простий place/view/directions/search; готові режими без нашої керованої сцени аватарів | Не обираємо головною картою можливостей |
| Maps JavaScript API | Власні інтерактивні маркери й шари поверх карти | Ціль наступного підключення |
| Routes API / Matrix | Порівнянні часи до кандидатних місць | Окремий серверний адаптер із лімітом |
| Вбудований покроковий навігатор | Додатковий мобільний продукт і платний Navigation SKU | Пізніше, якщо handoff у Maps недостатній |

Першоджерела: [URLs — Introduction](https://developers.google.com/maps/documentation/urls/get-started), [Embed — map modes](https://developers.google.com/maps/documentation/embed/embedding-map), [Routes — route matrix](https://developers.google.com/maps/documentation/routes/compute_route_matrix). Швидкість цих варіантів у Synera ще не порівнювалася. Для першого завантаження слід резервувати місце карти та завантажувати SDK після відкриття режиму й дозволу на зовнішній сервіс; виміряти час/трафік на Android до вибору остаточного бюджету.

Google global pricing, USD, місячні одиниці; перший платний діапазон до 100 000: Dynamic Maps — 10 000 безкоштовних loads, далі $7/1000; Compute Route Matrix Essentials — 10 000 безкоштовних elements, далі $5/1000; Embed — unlimited no-cost SKU. Navigation Request — 1000 безкоштовних, далі $25/1000. [Офіційна таблиця, Maps loads / Routes / Navigation](https://developers.google.com/maps/billing-and-pricing/pricing).

Приклад, не прогноз: 600 людей × 20 loads = 12 000 loads → $14. 600 × 2 планування × 3 людей × 10 місць = 36 000 elements → $130. Разом лише ці два SKU: $144 USD/місяць. Places, geocoding, AI, сервер, оператор і податки не враховані. Не змішуємо USD з CHF без відомого курсу. У симуляторі підтримується лише перший платний діапазон.

Billing та ключ потрібні для JavaScript API. До підключення: browser-key з дозволеними HTTPS origins та API restrictions; окремий server key, серверний контроль квот, доступний fallback. Google прямо пояснює, що **budget alert не зупиняє витрати**. Потрібні реальні квоти й контроль застосунку. [Billing](https://developers.google.com/maps/documentation/javascript/usage-and-billing), [Manage costs](https://developers.google.com/maps/billing-and-pricing/manage-costs).

Карта має показувати добровільно відкриту приблизну локацію, а не місце проживання. Точна локація зустрічі зберігає окремий чинний consent-flow. «Взаємодоповнююча голограма» означає приватну пропозицію знайомства з поясненими навичками; розкриття третього профілю/зв’язку та введення людей одне одному потребують дозволів. Публічна історія зустрічей — лише за окремою згодою. Рекламні ресторани чітко позначаються; спонсорство не змінює критерій придатності непомітно.

Для вибору місця пропонуємо minimax: мінімізувати найбільший час дороги серед усіх людей, потім різницю часів, потім суму. Спочатку фільтри: доступність, відкритість, ціна, погода/укриття, потреби мобільності й ліміти кожного. Якщо прийнятного місця немає — червоний стан і зміна умов, без обіцянки «завжди справедливо». Режим маршруту «прогулянка / прямо / спокійніше» обирає людина; психологічний профіль не вгадується.

## L: прозорі правила співпраці

Інтерфейс має давати відчуття сили спільної роботи через видимий внесок кожного, а не через непомітне керування чи статус «еліти». Висновок для дизайну: добровільний вибір, компетентність і зв’язок з людьми — корисні гіпотези мотивації. У [Ryan & Deci, 2000, pp. 70–74](https://selfdeterminationtheory.org/SDT/documents/2000_RyanDeci_SDT.pdf) описано зв’язок підтримки автономії/компетентності/relatedness із мотивацією. Це не експеримент Synera й не гарантія, що наш дизайн змінить поведінку підприємців.

Майбутня фасилітація має три добровільні рівні: тихий (лише на запит), допомога (короткі підказки з погодженою частотою), структурований круг (усі погодили порядок і правила). L може помітити **спостережуваний** невідповідний дедлайн/відкритий крок/запит на допомогу; не ставить діагноз, не вгадує почуття, не обіцяє визначення брехні. Твердження має статус «заявлено / джерело знайдено / оскаржено / неперевірено», із можливістю відповісти. Брутальна чесність — конкретно про твердження/умову, без приниження людини. Жарти необов’язкові; для конфлікту можна їх вимкнути.

Рівна видимість не означає рівної вартості роботи. Перед стартом: хто що дає, хто що отримує, сума/частки, власність, confidentiality, прийняття результату, право делегувати й припинити. «Call to honor» = зрозумілі правила слова/внеску, право на пояснення, ручний review і апеляція. Відмінний прибуток або відсутність кліку не є шахрайством. Ніякого автоматичного «рейтингу чесності» чи примусу.

Голос/відео: окреме room-membership і media-consent; кожен управляє своїм mic. Погоджений floor-control на сервері не вмикає чужий мікрофон/динамік. Завершення поточної думки, pass, pause і emergency stop залишаються доступними. Усі чують погоджену розмову; приховане відключення слухачів не є стандартом. Запис і транскрипція потребують окремої явної згоди всіх; переклад показує оригінал та невизначеність. Реальна realtime/video/voice інфраструктура тут не реалізована.

## Доступ, телеметрія й розвиток

П’ять контекстів: особиста чернетка → відкриті вибрані поля → домовленість двох → приватна проєктна кімната → персональний асистент. Це незалежні scopes, не сходи, де верхній рівень відкриває всі попередні дані. Мінімальне onboarding acceptance лишається; додатковий доступ запитується перед відповідною дією. Optional analytics не є умовою базового доступу.

Майбутня серверна схема triad: membership/authenticated actor, recipient ACL, revision/hash, own-vote writes, server clock, idempotency, revoke/leave/block, deletion/retention та audit metadata без raw-chat. Hosted AI бачить тільки дозволений redacted pack; приватні ідеї не йдуть у web research/training/іншим кімнатам. Group assistant потребує згоди всіх на конкретний контекст; відкликання одного зупиняє наступну обробку. Псевдонімізація сама по собі не робить бізнес-ідею анонімною.

Swiss FDPIC наголошує, що FADP застосовується до AI, потрібна зрозуміла інформація про обробку, а високий ризик вимагає DPIA. Це підстава проєктувати мінімальні поля й контроль доступу до запуску, не висновок про готову юридичну відповідність Synera. [FDPIC: AI and data protection](https://www.edoeb.admin.ch/en/ai-and-data-protection).

Телеметрія після окремого вибору: versioned UI event name, mode, coarse device, агрегований час/успіх кроку. Без тексту, precise GPS, audio, імен/контактів або психологічних висновків. Security/operational logs мають окрему мету й retention. Необхідно перевірити consent-off у runtime, видалення, ACL-негативні проби та правову основу. У новому локальному режимі collector відсутній.

Еволюція продукту: стабільні основні кнопки, opt-in feature flags і порівняння режимів; сезонні/market зміни як candidate patch → semantic regressions → preview → owner approval → canary → rollback. Iceberg-джерела не доводять автономного production self-rebuild; тут нові агенти/роутери/демони не створені. Body doubling/public focus timer — майбутній opt-in room сценарій, без соціального покарання за відпочинок.

## Що потрібно для повноцінного живого сценарію

1. Погоджений Google Cloud project, restricted key, exact paid cap та квоти; реальна карта з allowed профілями й Routes adapter; мобільний performance check.
2. Окрема reviewed triad server schema та RLS; два негативні actor/access cases; три реальні акаунти на трьох пристроях. Наявний bilateral кейс не переробляти на triad.
3. Погоджена media інфраструктура, три користувачі, микрофон/переклад/запис consent, disconnect/rejoin/stop acceptance.
4. Офіційні event/social approvals, джерела радара, throttling, opt-out, погоджена відправка, operational costs.
5. Privacy/DPIA за фактичними даними, серверні access/retention checks; pilot outcome evidence і тест цін. Checkout лише після затвердження тарифу та умов.

Це відкриті роботи, а не виконані можливості. Локальні тести, GitHub CI і публікація прототипу не заміняють їх.
