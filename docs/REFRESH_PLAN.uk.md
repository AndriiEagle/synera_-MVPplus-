## Роботи в порядку залежностей

| Крок | Конкретний результат | Приймання |
| --- | --- | --- |
| 1. Відновити сервіс | Знято історичне квотне обмеження організації; бюджет залишається $0 | Auth settings відповідає 200; немає 402 |
| 2. Перевірити справжній сценарій | Окремі синтетичні A/B/C, збереження між входами | A → B; C не бачить; B приймає; повторний вхід A бачить відповідь |
| 3. Довести реєстрацію | Погоджений SMTP або OAuth; правильний callback URL; підтвердження email збережене | Лист/вхід на кінцевому хості; відновлення доступу; обробка помилок |
| 4. Завершити вимоги пілоту | Видалення й строки зберігання, скарги/блокування, контакт оператора, захист від зловживань | Позитивні й негативні тести конкретних можливостей |
| 5. Опублікувати | Лише перевірені файли вебверсії на погодженому безплатному хостингу | HTTPS, заголовки захисту, реальний сценарій із двох пристроїв |
| 6. Наступний продуктовый етап | Карта, щоденник та інші можливості — у порядку потреб тестерів | Кожна можливість із власним прийманням |

Не обходити квоту новими акаунтами, не вмикати оплату і не видаляти старі дані заради запуску. Нова база вже створена в потрібній організації; повторне створення не виправляє HTTP 402.

## Окреме відновлення старого репозиторію

Локальні прямі AI-виклики вимкнено; 7 вставок ключів прибрано. Відкликання ключів у провайдера, очищення історії Git і перенесення старих користувачів ще не виконані. Новий статичний пакет не містить старого Flutter-коду, браузерних баз чи цих ключів.

Для публікації змін у GitHub потрібен перегляд точного diff. Історію з браузерним профілем не переписувати без окремого погодженого плану збереження та очищення.
