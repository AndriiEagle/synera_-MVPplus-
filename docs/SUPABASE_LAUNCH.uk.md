## Чому онлайн ще не запускається

Обидва запити до нового проєкту повертають HTTP 402:

- GET /auth/v1/settings
- GET /rest/v1/profiles?select=id&limit=1

Причина у відповіді: `exceed_db_size_quota`. Dashboard також показує **All services are restricted**. Це не помилка пароля й не проблема нового API-ключа.

На сторінці Usage: поточний розмір 0.026 / 0.5 GB (5%), новий проєкт приблизно 24.88 MB; egress, storage і MAU — нуль. Поточний розрахунковий період: **7 серпня — 7 вересня 2026**. Низький поточний розмір не гарантує негайного зняття історичного обмеження.

Supabase описує організаційний ліміт за середнім щоденним розміром за період. При новому періоді середнє починається заново, можливе запізнення зняття обмеження. Який старий проєкт і коли спричинив перевищення, ще не встановлено. [Офіційне пояснення](https://supabase.com/docs/guides/platform/database-size#fair-use-database-size-restriction).

## Після зняття обмеження

1. Запустити `node web_launch/health-check.mjs`; HTTP 402 має зникнути.
2. Підготувати синтетичних тестових користувачів через Auth і пройти сценарій A/B/C із повторним входом. SQL-тест не замінює цей крок.
3. Налаштувати підтвердження email та callback URL на погодженому хостингу. Стандартний SMTP Supabase не обслуговує довільну аудиторію; він призначений для тестів учасниками організації. [Деталі](https://supabase.com/docs/guides/auth/auth-smtp).
4. Завершити потрібні пілоту видалення/утримання даних, скарги, блокування та правила користування; перевірити їх окремо.
5. Публікувати лише перевірений статичний пакет. Оригінальну історію репозиторію не завантажувати як сайт.
