# Комплект власника

1. Почни з CHECKLIST.uk.md. Нічого не застосовано й не опубліковано.
2. 00-inspect.sql — лише каталоги; 10-migrate.sql — атомарний conditional apply відсутніх повних відомих міграцій. Невідомі function body/атрибути, RLS policy definition, частковий marker або відсутня база r8 — RAISE і rollback усіх DDL. Повторний apply пропускає завершені міграції. RLS probes створюються й видаляються всередині тієї самої транзакції; назовні вони не публікуються. Історичний GRANT meeting_address після нової міграції навмисно відсутній; фінальна перевірка враховує REVOKE.
3. 11-acceptance-disposable.sql — **лише EMPTY disposable database** з сумісними provider identity fixtures; створює базу/міграції тимчасово й закінчується ROLLBACK. Усі 11 вихідних suites включені: base, case-state, meeting-status-guard, meeting-location, group-room, outcome, address, message consent, erasure surfaces/lifecycle, stack-invariants. Fixtures outcome/address/message/erasure відтворюють контракти наявних JS runners. Кожний набір відкочується до SAVEPOINT; фінальний ROLLBACK прибирає весь replay.
4. Локальний PostgreSQL тест використовує **identity shim** з neon/local_acceptance.mjs. Це не signed JWT і не перевірка живого Neon. У Neon SQL Editor не підміняй auth.uid() і не запускай fixture suite на production. Якщо справжній disposable Neon не підтримує fixture JWT context, це HOLD саме для цього replay; локальне приймання не дозволяє підміняти provider identity. Production-файл має окремі catalog/definition/grant checks; реальні OTP, RLS і сценарій приймаються з двох телефонів.
5. acceptance-sources.json зберігає всі вихідні suites і SHA оригінальних байтів та нормалізованого SQL (лише CRLF → LF). manifest.json містить commit, вихідні SHA, ZIP SHA/size, кожний upload file та SHA артефактів. ZIP = PUBLIC_ASSETS + _worker.js + _routes.json + release.json, без SQL/docs/tests/maps. Незмінений neon/build.mjs виконується в sandbox; лише Date для release.json фіксується на час commit. Окремий тест запускає canonical build без цього hook і порівнює всі файли після нормалізації тільки built_at.
6. Межі: 30 хв — сценарій ПІСЛЯ account/backup/restore/local acceptance gates; 2 хв — ціль Worker rollback, не гарантія DB restore. Lossless schema-down джерелами не визначено: production зберігає additive SQL або відновлюється з перевіреної точки за окремим рішенням власника. Після merge перегенеруй kit з чистих build inputs; новий невідомий env/migration зупиняє generator для review.
