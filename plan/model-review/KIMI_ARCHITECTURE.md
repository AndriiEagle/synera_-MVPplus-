1. **high | Ambiguous "relevant next action" scope on revocation** — The contract says material edit, expiry, revocation, or withdrawal "invalidates the relevant next action" but never defines the invalidation graph (e.g., does terms-approval withdrawal invalidate an already-issued introduction request, or only future ones?). Ambiguity lets one reader cascade invalidation and another not. **Correction:** add a matrix mapping each invalidation event to exactly which states are voided and which are preserved. **Proof:** two implementations satisfying the current text produce different states for the same event sequence; a matrix yields exactly one reachable state.

2. **high | "Non-binding business case" vs binding approval semantics conflict** — The flow requires both parties approve the same case/version/hash, yet the case is declared non-binding. If approval has no binding effect, its evidentiary role in D3 ("two authorized people and fresh remote evidence") is undefined; an adversary can repudiate approvals. **Correction:** define what approval attests to (acknowledgment of terms, not obligation) and its legal-neutral evidentiary weight. **Proof:** without a defined attestation semantics, an approval artifact proves nothing and the hash ceremony is decorative.

3. **high | "Pure canonical material payload/version/hash" has no canonicalization rule** — "Canonical" is asserted but serialization (field order, whitespace, encoding, float format) is unspecified; two correct compilers can produce different hashes for identical content, breaking "same case/version/hash" matching. **Correction:** pin one deterministic canonicalization (byte-exact spec) as part of the contract. **Proof:** semantic equality ≠ byte equality; approval compares hashes, so unspecified serialization makes the equality test implementation-dependent.

4. **medium | Paid-service mode leaves compensation "unresolved until approved" with no terminal state** — If compensation never reaches approval, no timeout, expiry linkage, or abandonment path is defined; the case can hold a live introduction gate indefinitely while other consents expire independently, creating a wedged state. **Correction:** define expiry interaction and a closed/abandoned terminal state with invalidation of downstream actions. **Proof:** the state machine has no transition out of "compensation unresolved," so it is a liveness trap reachable by normal flow.

5. **medium | Hybrid leg independence conflicts with shared consents** — "Every named leg must pass independently," but permissions (case disclosure, terms approval) appear pair-global. If one leg fails, does the pair-level approval stand for the remaining legs? Undeclared. **Correction:** state whether approvals are per-leg or per-case, and how partial leg failure mutates the case hash/version. **Proof:** leg-level failure is an input the approval logic must consume; with pair-global approval, two outcomes (whole-case void vs. leg-stripped case) both satisfy the text.

6. **medium | Missing-fields → needs_information lacks field enumeration per mode** — "Missing new fields means needs_information" is safe, but the required-field set per mode (exchange/paid_service/referral/hybrid) is only partially listed; an implementer can silently treat unlisted fields as optional, collapsing mode distinctions. **Correction:** provide an exhaustive required/optional field table per mode. **Proof:** "new fields" is an open set; an open precondition cannot be falsified, so the safeguard is untestable as written.

7. **medium | D1–D5 gate criteria are non-checkable as stated** — "Fresh remote evidence" (D3), "fixed real cohort" (D4), and "commercial launch" (D5) have no quantitative or procedural acceptance criteria, while overnight target is D1; nothing prevents drift past D1 without criteria. **Correction:** attach measurable pass/fail criteria and an explicit gate artifact per D-stage. **Proof:** a gate without a predicate admits any evidence; stage progression is then unfalsifiable.

8. **low | "Independent reviewer cannot accept own work" lacks identity/attestation mechanism** — With max 3 active participants including an integrator who writes, role collision is possible (integrator reviews own integration) and no attestation artifact ties reviewer identity to acceptance. **Correction:** require signed review markers naming author ≠ reviewer per task hash. **Proof:** independence is a relational property; without recorded identities it cannot be audited after the fact.

**Mutation tests:**
- M1: Mutate canonical payload field ordering/whitespace only; system must reject the case as a hash mismatch, proving canonicalization is enforced, not assumed.
- M2: Revoke case-disclosure consent after terms approval but before introduction request; introduction must be invalidated and state must be re-derivable from the invalidation matrix alone.
- M3: Submit a hybrid case where one named leg fails and the other passes; assert the declared per-leg vs per-case behavior exactly, with no legacy joint_project fallback.

**Proposals to reject:**
- R1: Reject adding a duplicate or "temporary" matcher/router/ledger for the new modes; contract explicitly forbids duplicates and extension of the existing matcher is mandated.
- R2: Reject treating missing new fields as legacy joint_project data to preserve compatibility; contract requires needs_information, not legacy corruption.
- R3: Reject any D1 scope creep enabling deployment, messaging, payment, recording, or live-user action "for testing"; the overnight target explicitly prohibits all live-user actions.
