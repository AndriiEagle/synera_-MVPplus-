# Source-linked task recipes

Read only the recipe needed for the current situation. Use plain language and exact file pointers; no extra encoding layer or artificial response cutoff.

## Repair an existing behavior

Outcome: the exact user action and expected visible result.
Evidence: current checkout/commit, relevant files and prior proof, observed failure.
Ownership: files this worker may edit; other workers and dirty boundaries.
Preserve: consent, actor identity, explicit send, draft continuity, default design.
Acceptance: semantic RED → narrow fix → affected gate → adversarial check.
Return: diff, reproducible command/result, proof limits, next dependency.

Example: “A manual retry after an ambiguous message acknowledgement must not create a second row for the same intent. Inspect the existing message owner and current acceptance first. Preserve deliberate repeated messages after a confirmed success and auth changes. Return the observed behavior, changed files and exact oracle; do not claim cross-reload persistence unless tested.”

## Model an early cohort

Decision: which cohort size, acquisition experiment or free/paid boundary is being compared.
Inputs: provenance, units, assumed ranges, activation gates, initial capacity and horizon.
Mechanism: opt-in signup → active participants → bilateral compatible/time-feasible pairs → completed and accepted outcomes → voluntary retention/referrals.
Money: fixed cost, per-action cost, free quota, optional payment activation, voluntary support separately.
Acceptance: zero-input and boundary cases, people/time/cash conservation, reproducible randomness, sensitivity and explicit uncalibrated assumptions.
Return: executable model, inputs/results, scenarios, what observation would change the decision. Avoid a single “critical mass” number independent of compatibility and time.

## Prepare a live pilot

Read the current rollout review and session authorization. Bind to exact database/branch, SQL source, previous release/recovery, manifest and readiness flags. Before changes, verify the reviewed artifact still matches and recovery/cost gates hold. Preserve the previous release. If the required approval is absent, finish only independent local preparation, name the one missing permission and keep the candidate reviewable.

Do not turn local PG tests into real signed-session acceptance; real users and physical Android are their own checks. Never rerun a full base migration because a new URL is missing. Do not expand a ten-user pilot into mass registration without an accepted capacity/cost decision.

## Review a result independently

Give the reviewer the current raw inputs, skill path and requested outcome. Omit the expected verdict. Ask for a bounded acceptance exercise using owned scratch paths and existing tools. The reviewer must name what evidence supports or contradicts the requested result, and may return “unproven.” The parent checks the produced artifact before accepting it.

## Report or hand off

Use a short readable card: outcome; artifact/commit; decisive verification; live/synthetic boundary; one next action. Separate measured provider USD, local tokenizer proxy and unavailable subscription savings. Keep original source locators recoverable when shortening context. Report a pending task as pending; never infer success from its creation ID.
